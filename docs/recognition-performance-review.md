# 识别全流程性能检查

检查日期：2026-10-18。范围：图片、文字、手动克重、手动份数、更换菜品、候选选择、结果展示及保存。
基于当前工作区代码静态检查；未连接真机，也未请求用户配置的模型服务。
以下优先级按建议实施顺序排列，收益为条件性判断，不代表已测得的端到端加速比例。

## 本轮实施状态

已完成以下改动，并通过新增的请求次数、并发、慢网与取消测试：

- 手动克重先做可靠离线匹配，未命中才请求名称标准化；本地探测未命中不增加最终匹配失败计数。
- 手动份数的营养解析与估重并发执行，任一失败或用户取消时取消同组剩余工作。
- 同餐按完整中英文查询与原名去重；独立查询最多并发 3 个，保持组成 ID、重量和原有引用。
- 同次查询复用在线响应判断待确认候选，不把网络失败或空结果长期缓存。
- 候选先显示本地结果，联网结果完成后更新；关闭或选择后取消搜索，防止旧搜索覆盖新状态。
- 自动匹配取最高分而不完整排序；存在性检查找到即停；带查询浏览不再构建无用的全库浏览列表。
- 个人记忆全量读取后的 JSON 解码移到 IO dispatcher。
- 图片准备、缓存读取、记忆读取、各轮模型、营养匹配、图片保存及缓存写入分阶段计时，保存在当前任务记录的 `phaseDurationsMs`，成功和失败均保留。并发阶段的耗时可以重叠，不能把各阶段简单相加当作总耗时。现有诊断页和 30 天聚合指标尚未增加阶段展示。

### 第二阶段

- 中国库在加载时预计算中文名称、别名、做法和主名称二元字串；一次查询的别名、字串与做法也只解析一次。只有中文身份精确命中时才执行其英文自动采用校验，不影响宽泛候选的评分。
- 优化前冻结了 26 组真实库检索结果，包含全部中国库候选顺序及自动匹配结果；优化后逐项对照通过，涵盖别名、形态、生熟、加工与中英文检索。
- 图片上传、缓存摘要和保存复用一个准备结果中的 JPEG 字节、Base64 与摘要；图片缓存指纹仍使用原算法，保持已有缓存兼容。缓存等待确认前保存已准备好的图片，确认后或进程恢复后直接读取内部文件，避免再次解码与 JPEG 压缩。图片尺寸与质量参数不变。
- 个人记忆按完整数据库行内容复用解码结果，未变化时复用整个解码快照，部分变化时复用未变的条目。每次仍读取最新数据库行，确保其他 Repository、导入、删除、清空或同 ID 修复都能立即反映，而不依赖异步失效通知。
- JVM 测试覆盖图片字节与旧指纹一致、缓存确认后的任务恢复，以及个人记忆更新与损坏记录修复；真实 FileProvider 图片往返另有 Android 仪器测试。

### 第三阶段与速度对比

- 中国库加入候选倒排索引，覆盖精确身份、别名、主名称二元字串、单字包含与英文词召回；仍执行原有评分和自动采用校验，保留来源顺序。
- 已命中的营养查询在生成检索词之前返回缓存，进一步减少重复文本计算。
- 除真实库快照对照外，索引增加全部 1–4 字短名称组合的穷举召回一致性检查，覆盖单字、子串和二元字串。
- 使用优化前 Git 版本 `d7c98c0f39920bfc91f76cf1048dacdd47503764` 的原始匹配代码，在同一 JVM 交替测量，核对结果一致。详细样本、统计、环境和复现步骤见[速度对比报告](performance/recognition-2026-10-18/report.md)。

在线回退请求从 16 次降到 4 次；文字核心流程含模型调用从 17 次降到 5 次。首次加载项使用新客户端，但 JVM 已预热且未清空系统文件缓存。这里没有测手机界面、真实图片编解码或真实模型服务；这些结果不能当作手机端到端提速比例。

下文保留检查时的基线与建议，行号对应检查时版本。尚未实施的主要项目包括个人记忆的数据库查询复用、复核输出协议修改和保存后持久后台学习。图片质量与复核准确性相关修改需先用真机固定样本验证。

### 图片识别流程的并行准备

- 读取个人记忆与首次视觉模型请求并行，首次结果返回后再判断原有稳定记忆快速路径。
- 需要视觉复核时，最多预查 12 组初始组成的离线营养引用，最多并发 2 项；与二次视觉模型请求重叠，不发起额外在线请求，不提前更新匹配诊断或自动采用候选。
- 复核结束后按最终名称、中英文查询及数据库开关使用缓存；修改后的身份不会套用旧组成引用。未完成的推测工作取消，取消或替换任务也会终止其子工作。
- 一次图片任务复用同一份提示词配置快照；默认与自定义的视觉识别／复核提示词保持原有内容。
- 分阶段计时新增 `NUTRITION_PREFETCH`；其耗时与模型复核重叠，不能与模型时间相加当作实际总等待。
- 调度测试使用虚拟时间验证：300ms 记忆读取、500ms 首次视觉请求、500ms 复核和 400ms 离线预查，可在 1000ms 的模型窗口内完成准备。该测试验证并发顺序，不是实际 API 速度测量；上面的速度表仍是此前数据库与文字核心流程的实测记录。

## 检查时的流程

- 图片：缩放与 JPEG/Base64 编码 → 图片缓存检查 → 读取个人记忆 → 视觉识别 → 二次视觉复核（符合稳定记忆策略时可跳过）→ 营养匹配 → 图片与缓存持久化 → 结果交接 → 再次读取个人记忆并生成建议 → 页面展示。
- 文字／更换菜品：模型拆解 → 营养匹配 → 结果交接与记忆建议。
- 手动克重：模型标准化名称 → 营养查询。
- 手动份数：模型估重 → 模型标准化名称 → 营养查询。
- 候选弹窗：离线 USDA 排序 → 串行在线搜索 → 中国库排序 → 合并结果并展示。
- 保存：批量写入记录 → 等待诊断写入 → 逐菜学习个人记忆 → 清理任务并反馈成功。

## 已有优化与测量边界

上一轮已加入 USDA 关键词索引、可靠离线命中优先返回、本地候选存在时省去额外联网搜索，并预编译部分正则。
电脑 JVM 上，真实库的 9 组查询评分测试为全扫描 747ms、索引召回后评分 23ms，评分记录数从 122,319 降至 2,412，结果与排序一致。
这只衡量索引加载后的候选评分，不包含冷启动加载、图片、模型、网络、展示或保存。已有 269 项单元测试通过。

## 第一批：测清阶段耗时，消除明确的重复与串行等待

### 1. 分阶段计时，纠正“匹配中”的统计范围

证据：`RecognitionDiagnostics.kt:19` 只记录总耗时；`RecognitionService.kt:310` 左右进入 MATCHING 后，还执行记忆辅助、营养匹配、图片写入和缓存序列化。`RecognitionCoordinator.kt:287` 的记忆建议又发生在服务完成以后。

改法：使用单调时钟记录图片编码、缓存查询、记忆读取、首次模型、复核模型、离线匹配、在线查询、图片写入、结果交接、记忆建议和保存耗时；另记录模型请求次数、在线请求次数、去重前后组成数，以及缓存命中／冷加载状态。页面首帧和卡顿用真机 tracing 验证。
只保存阶段与数值，不保存食物名、图片或凭证。区分“服务完成”和“结果可操作”，按路径与冷／热启动汇总 P50/P95。

收益：先判断用户等待的实际来源，避免把模型延迟和文件写入误认为数据库计算慢。

### 2. 手动克重先尝试可靠本地匹配

证据：`RecognitionService.kt:185` 的 MANUAL_GRAMS 无条件先调用 `normalizeFoodQuery`，即使“米饭”“北豆腐”已有本地匹配能力。

改法：先使用原始名称查询离线库，确认可靠命中后直接计算；未命中再标准化并执行原有后续查询。首次尝试不能联网，否则可能新增一轮网络等待。保留中文原名约束、生熟与做法校验。

收益：常见名称可省去一次完整模型请求。不能假设所有中文名称都能本地命中。

### 3. 手动份数取消两次模型请求的串行依赖

证据：`RecognitionService.kt:208` 先等待份量估重，再在 `:216` 标准化名称；标准化只依赖食物名，不依赖估重结果。

改法：先本地匹配；若需要标准化，可用结构化并发同时执行估重与名称标准化，最后合并结果。后续也可评估合并为一次模型返回“克重＋检索词”，但合并需修改提示词、解析和覆盖自定义提示词的兼容规则。

收益：并发后这两段等待可由相加变为接近较慢的一段，实际效果取决于服务端并发限制。失败／取消应终止同组剩余请求。

### 4. 按查询语义去重组成，再有限并发匹配

证据：`FoodDataCentralClient.kt:93` 仅按组成 ID 去重，`:94` 使用串行 `associate`。不同菜里的相同油、盐、米饭等仍可能拥有不同 ID。缓存只保存成功的引用，未命中和候选存在性不会复用。

改法：在单次识别内，以完整中英文查询和原始名称、数据库开关、联网配置作为键，复用“自动引用＋候选存在性”；保持每个组成自己的 ID 和重量。对独立查询设置 2–4 个并发上限，并对同键进行中的请求合并。
不能只按英文查询或食物名去重，避免丢失原名、生熟或加工约束。并发前核查诊断回调的线程安全，避免并发写 `MutableStateFlow.value.copy(...)`。

收益：多菜、多组成和部分需要联网时明显；纯本地的小餐不保证受益，过度并发可能增加 CPU 竞争。

### 5. 合并一次匹配中的在线召回结果

证据：`lookup` 的 `findOnlineMatch` 在线结果没有可靠命中后，`enrich` 的 `hasCandidates` 在本地也无候选时，会再次发起相同词的在线搜索。前者请求 8 条，后者请求 1 条；`:345` 还逐个等待检索词。

改法：一次召回同时产出可靠引用与待确认候选标记，复用原始在线结果；优先做请求内缓存，避免长期缓存失败。若加入短期缓存，应区分成功空结果与超时、断网、限流，并限定大小和失效时间。
为整组在线查询增加总时间预算；目前连接／读取超时是单次请求限制，不是整餐耗时上限。超时只能标记“未验证”，不能误报“确认无候选”。

收益：数据库没有收录的食物和网络异常时，可减少重复等待与请求次数。

## 第二批：减少展示等待和本地 CPU 工作

### 6. 候选弹窗先显示离线结果，再补联网结果

证据：`FoodDataCentralClient.kt:148` 在线搜索位于中国库排序之前，整个函数等所有来源完成后返回；`ComponentSearchInteractor.kt:179` 只在最终返回时更新列表。

改法：离线 USDA 与中国库先合并展示，在线结果随后更新。将“本地结果已可选”和“联网补充中”分别表示，允许先选择可靠本地结果。保持稳定条目键和选择状态，防止排序更新造成误选。
`closeReview():130` 还应取消搜索，与 `closeDraft()` 一致；当前关闭复核弹窗只清状态，未主动取消请求。当前 UI 是按钮触发搜索，并非每键自动搜索，无需为了性能先加输入防抖。

收益：在线服务慢时，本地候选无需陪同等待；关闭弹窗及时释放网络工作。

### 7. 为中国库预计算查询无关的特征

证据：`FoodDataCentralClient.kt:246` 的 `rankChina` 仍全库遍历；每条记录重复执行中文别名提取、生熟判断和英语特征处理。`lookup` 可能用不同召回策略调用两遍中国库，未命中后还要做候选搜索。

改法：加载时预计算条目中文身份、别名、生熟与英文词集合；每次检索只计算一次查询特征。自动匹配可按完整中文身份／别名索引召回，宽泛候选可另用二元字串索引。校验特征与索引召回都需和旧实现逐条对照。

收益：中文查询和未命中的热路径减少分配与正则工作；中国库只有 1,635 条，收益应实测后再决定是否做更复杂索引。

### 8. 自动匹配取最佳项，存在性检查找到即停

证据：`rankUsda`、`rankChina` 总是生成并排序完整结果；自动匹配只拿 `firstOrNull()`，候选检查只拿 `isNotEmpty()`。`browseOffline` 即使带查询，也先构建不用的 `sourceItems`。

改法：共用评分与安全校验，提供稳定的 best／any／top-K 三种消费方式；同分 best 保留先出现的来源，any 不必排序。把无查询浏览的列表构建放进对应分支。

收益：减少局部分配与排序，主要是索引优化后的后续 CPU 优化，优先级低于减少网络请求。

### 9. 复用个人记忆快照，将解码与匹配移出主线程

证据：图片服务 `RecognitionService.kt:281` 读一遍个人记忆，结果交接时 `RecognitionCoordinator.kt:293` 再读一遍；`PersonalFoodMemoryRepository.kt:26` 在 DAO 返回后直接解析所有 JSON，未指定后台 dispatcher，完成页调用者来自 `viewModelScope`。

改法：Repository 在后台完成解码，并提供可失效的只读快照或索引；精确名称与别名优先走索引，必要时再相似匹配。用版本号或保存后的失效机制保证学习记录更新后不会读到旧数据。

收益：个人记忆多时减少结果到达后页面迟迟不出现／卡顿；少量记忆下不是主要瓶颈。

## 第三批：图片、模型与保存

### 10. 规范化图片只做一次，复用 JPEG 字节和摘要

证据：`FoodImages.kt:20` 已按最长边 1024 缩放并处理 EXIF，这部分已有合理保护。随后 JPEG 字节变 Base64，缓存对 Base64 求摘要，`:90` 保存时又解码 Base64 并对字节求摘要。图片缓存确认后，`resolveImageReuse` 重新启动任务，再次执行编码和缓存读取。

改法：用一个准备结果持有 JPEG 字节／文件、摘要和按需生成的 Base64；确认缓存复用时沿用已经准备的文件。可让内存中的图片结果缓存复用同一个实例，避免每次构造并解析整个 JSON 文件；持久化仍需进程恢复和过期清理。

收益：减少准备阶段分配和重复解码；相较模型往返通常较小。不要直接降低分辨率或 JPEG 质量，先用细小配料、包装文字和暗光图验证识别质量。

### 11. 优化复核请求成本，保留准确性门槛

证据：`FoodRecognitionClient.kt:430` 等首次完整结果后，`:437` 发第二次视觉请求，再上传同图和首次完整 JSON，并等待完整复核输出。只有严格的稳定个人记忆策略允许跳过。

改法：先计量每轮输入／输出字节与耗时，再评估让复核只返回修改项或“无需修改”；验证未修改组成、菜品层级、重量和自定义提示词是否都能正确保留。可以在复核期间预取首次结果中的离线营养匹配，最终只复用查询约束完全一致的组成，并丢弃被复核修改的项。
不要仅凭模型自报高置信度移除复核。流式预览可改善等待感，但不会自动减少完整 JSON 就绪时间。

收益：模型阶段可能是总耗时的大头，但没有服务端测量前不能承诺具体降幅；修改输出协议需固定样本集评估准确率。

### 12. 保存成功反馈不必等待所有可选工作

证据：`AddFoodViewModel.kt:991` 附近批量保存后，仍等待诊断落库、逐菜 `learnAfterSave`，最后才清任务并显示成功。学习新菜的别名匹配可能再次解码全部记忆。

改法：记录提交后及时反馈成功，将可选诊断与学习交给应用级、可追踪的后台任务；如要求进程退出后仍保证学习完成，应使用持久任务／事务消息机制，而非页面作用域的 fire-and-forget。批量学习可复用一次记忆快照，并控制事务长度。

收益：多菜和记忆数据量大时缩短“保存中”，不影响已经提交的饮食记录。

## 验证顺序

1. 增加分段计时，在真机测一菜、多菜、未知食物、重复照片和长历史记忆；区分冷／热启动。
2. 做手动本地优先、份数并发、请求内去重与在线结果复用；断言模型／HTTP 次数减少且引用相同。
